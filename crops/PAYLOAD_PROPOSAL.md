# Crops payload: the second case

CRO to design, 2026-07-29, answering `design/PAYLOAD.md`. Under D-030
the channel-to-design shape is discovered rather than specified, and
crops is the second implementation, so this argues with the fire shape
where crops breaks it and adopts it where it holds.

Design asked for one thing specifically, the qualifier field, and said
they would change the fire payload to match rather than have crops match
a shape they already believe is wrong. Section 1 is that proposal. The
rest follows from the three things they flagged as fires-specific.

## 1. `qualifiers`: the field design asked for

**Proposal: a list of objects on the instrument block, never a string,
and never hand-written.**

```
instrument_block: {
  ...,
  qualifiers: [
    { kind: "single_outcome_source",
      text: "One production source (FAOSTAT). No standalone European
             series exists in USDA PSD to check it against." },
    { kind: "net_of_adaptation",
      text: "Measures climate stress net of agricultural adaptation.
             Stable variance is consistent with rising stress offset by
             irrigation, breeding and management." }
  ]
}
```

**Why a list and not a string.** Crops pairs routinely carry two or
three at once. A Spanish wheat row is single-outcome-source *and*
rank-based rather than multiple-based *and* not ENSO-linked. Three
caveats concatenated into one string is prose, and prose is what D-051
exists to stop.

**Why `kind` as well as `text`.** The kind is what a CI check can
assert, per D-046. A renderer can be tested for "every qualifier kind
present in the payload has a rendering"; it cannot be tested against
free text. It is also what lets design decide that
`single_outcome_source` renders as a badge and `net_of_adaptation` as a
footnote, without design ever having to parse a sentence.

**Why the text is computed and never typed.** The platform contract
forbids free-text fields that are not computed, because both content
defects that week were hand-curated strings that stopped tracking their
data. So `text` is generated by the channel from the condition that
triggered it, with the source name and numbers interpolated from the
same data being described. If the condition stops holding, the qualifier
disappears; it cannot be left behind.

**One rule attached, and it matters more than the shape.** An **empty
list is a positive assertion** that the channel checked and no qualifier
applies. It is not the same as the field being absent, which is a bug.
Design should be able to fail a build on a missing `qualifiers` key and
render an empty one as a clean number with confidence.

## 2. `publishable`: design is right, and it is mine

Accepted without reservation, including the reasoning: a template that
quietly drops rows it was handed is worse than one that shows
everything, because the channel then cannot tell from the page whether
its own gate worked.

**But not by omission.** Omitting a suppressed pair makes the gate
invisible in exactly the way design objects to. Instead:

```
{ pair: "Iran / Barley",
  publishable: false,
  publishable_from: "dekad 31",
  suppressed_because: "Correlation with final production is -0.51 at
                       this point in the season: a confident signal
                       pointing the wrong way. Readable from dekad 31." }
```

Design renders a not-yet-readable state, never the number. The channel
owns the decision, the page shows that a decision was made, and a reader
can see that nineteen pairs exist and three are not yet readable. That
is strictly better than silence in either direction.

## 3. `magnitude` replaces `multiple`

Design already knows `multiple` is not universal: crops ranks Nth of 26,
El Nino's magnitude is a signed anomaly with no multiple at all, fires
uses a ratio. One kind-tagged object rather than three fields:

```
magnitude: {
  kind: "rank",            // rank | multiple | anomaly
  value: 24, of: 26,
  direction: "high",       // which end is bad, since it differs
  basis: "same dekads, 2001-2025"
}
```

`basis` is not optional. The editorial standard already requires that
every comparison names its basis, and this is where it lives so it
cannot be dropped in layout.

## 4. `instruments` as a list

Confirmed by crops, as design predicted. Fires has two instruments;
crops has six on every pair (cumulative vegetation, current vegetation,
water satisfaction, rainfall, soil moisture, temperature), and the
number is a property of the channel, not of the schema. `detections` and
`area` as fixed keys do not survive contact with a second channel.

`z` moves onto the instrument block for the same reason: crops has six
of them and they disagree, which is the point.

## 5. What crops does not have

`volume_context` has no crops analogue and I would not invent one. The
fires idea, large but normal, has no meaning for a rank-based claim.

## Worked example: Spain, wheat

Everything above in one real row, using real values.

```
pair: "Spain / Wheat"
attribution: "non_enso"
evidence_basis: "measured"
publishable: true
claim: "Spanish wheat is in the better half of its 25-year record for
        this point in the season."
magnitude: { kind: "rank", value: 18, of: 26, direction: "low",
             basis: "same dekads, 2001-2025" }
instruments: [
  { name: "Vegetation, cumulative", value: 0.24, z: 0.24,
    baseline_mean: -0.01, baseline_span: "2001-2025",
    source: "JRC ASAP, FPAR cumulated z-score, crop mask, growing cycle",
    as_of: "2026-07-11", authorship: "agency", qualifiers: [] },
  ...
]
qualifiers: [
  { kind: "single_outcome_source", text: "..." }
]
```

Note `authorship: agency` on the instrument and `tls_built` on the
country-level aggregation and rank, per D-021. The ASAP value is JRC's;
the rank against 25 years is ours. Same row, two authorship values, and
that distinction is why the field exists.
